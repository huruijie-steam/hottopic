# HotTopic 热点监控工具 —— 需求文档

> 版本:v1.0
> 状态:评审中
> 参考项目:[yupi-hot-monitor](https://github.com/liyupi/yupi-hot-monitor)(AI 热点监控工具)
> 技术底座:Spring Boot 4.0.7 + Java 17(当前骨架)

---

## 1. 项目背景与目标

### 1.1 背景

作为关注 AI 领域动态的开发者,需要**第一时间**发现最新热点(如大模型发布、技术框架更新),人工搜索效率低且容易遗漏。本项目的目标是复刻并改进开源项目《AI 热点监控工具》:让系统代替人工,自动从多个信息源聚合抓取与监控关键词相关的内容,借助 AI 完成真假识别、相关性分析和智能摘要,并通过实时推送和邮件把重要热点第一时间送达。

### 1.2 目标

- 输入关键词即可**自动、持续**监控相关热点(30 分钟一轮);
- 聚合 **8+ 信息源**,覆盖国内外主流平台;
- 用 AI 过滤垃圾/虚假内容,只保留**真实、相关、重要**的热点;
- WebSocket 实时推送 + 邮件通知,重要热点不遗漏;
- 提供"全网搜索"能力,主动查询任意关键词;
- 沉淀为可复用的 **Agent Skills 技能包**,让 AI 编程工具也能直接使用监控能力。

### 1.3 非目标(本期不做)

- 不做用户登录/多租户权限体系(单用户本地工具);
- 不做分布式部署与消息队列(单机够用,架构预留扩展);
- 不做移动端原生 App(响应式 Web 即可)。

---

## 2. 用户角色与核心使用场景

| 角色 | 场景 |
|------|------|
| 热点监控者 | 添加监控词 → 开启监控 → 系统每 30 分钟自动巡检 → 收到新热点推送/邮件 → 在页面查看、筛选、阅读热点 |
| 主动搜索者 | 在搜索页输入任意关键词 → 多源聚合搜索 → 按热度/相关性排序浏览结果 |

## 3. 功能需求

> 优先级:P0 = 必须实现(第一版上线);P1 = 重要(第二版);P2 = 可选(后续迭代)。

### 3.1 关键词管理(P0)

| 编号 | 需求项 | 说明 | 优先级 |
|------|--------|------|--------|
| KW-1 | 添加关键词 | 支持输入任意文本关键词(英文/中文/混合),自动去重 | P0 |
| KW-2 | 关键词列表 | 展示全部关键词,含分类、状态、关联热点数、创建时间 | P0 |
| KW-3 | 激活/暂停 | 每个关键词可独立开关;暂停后定时任务跳过该词 | P0 |
| KW-4 | 编辑/删除 | 支持修改关键词文本;删除后关联热点保留(keywordId 置空) | P0 |
| KW-5 | 分类标签 | 可选分类(如 AI/前端/后端),用于筛选 | P1 |

### 3.2 热点采集(P0)

| 编号 | 需求项 | 说明 | 优先级 |
|------|--------|------|--------|
| HC-1 | 定时巡检 | 每 30 分钟自动巡检一次所有激活关键词(可配置间隔) | P0 |
| HC-2 | 手动触发 | 提供接口/按钮立即执行一次巡检 | P0 |
| HC-3 | 多源聚合 | 并行抓取 8+ 数据源(见 §5),单源失败不影响整体 | P0 |
| HC-4 | 账号检测 | 当关键词恰好是微博/B 站/推特账号时,直接拉取该账号最新内容 | P1 |
| HC-5 | 去重 | 按 URL 标准化(去尾部斜杠、www)跨源去重 | P0 |
| HC-6 | 新鲜度过滤 | 只保留 7 天内的内容(无发布时间的结果保留) | P0 |
| HC-7 | 来源优先级 | 聚合结果按 Twitter > 微博 > B站 > HN > 搜狗 > Bing > Google > DDG 排序 | P1 |
| HC-8 | 处理配额 | 每轮 AI 分析数量受控:Twitter 最多 15 条,其他来源合计 10 条(防烧钱) | P0 |
| HC-9 | 幂等入库 | 同一 (url, source) 不重复入库;新热点自动创建站内通知 | P0 |

### 3.3 AI 智能分析(P0)

| 编号 | 需求项 | 说明 | 优先级 |
|------|--------|------|--------|
| AI-1 | 查询扩展 | 用 AI 将关键词扩展为 5-15 个变体(大小写/缩写/中英对照),结果缓存;无 key 时降级为纯文本拆词 | P0 |
| AI-2 | 真假识别 | 判断内容是否为真实信息,排除标题党、假新闻、营销软文(isReal) | P0 |
| AI-3 | 相关性评分 | 0-100 分,要求"直接提及关键词"才能高分;纯同领域沾边 30-50 分 | P0 |
| AI-4 | 关键词提及标记 | 标记内容是否直接提及关键词(keywordMentioned) | P0 |
| AI-5 | 重要程度分级 | low / medium / high / urgent 四档 | P0 |
| AI-6 | 智能摘要 | 一句话说明"此内容与关键词的关联"(不是内容简介) | P0 |
| AI-7 | 预匹配增强 | 先用扩展词做纯文本预匹配,把命中结果注入 prompt(命中→宽松审核;未命中→严格审核) | P0 |
| AI-8 | 三重过滤规则 | ① 非真实内容剔除;② 相关性 < 50 剔除;③ 未提及关键词且相关性 < 65 剔除 | P0 |
| AI-9 | 失败兜底 | AI 不可用/超时/解析失败时,用预匹配结果生成默认评分,流程不中断 | P0 |

### 3.4 热点展示与检索(P0)

| 编号 | 需求项 | 说明 | 优先级 |
|------|--------|------|--------|

| HP-2 | 统计概览 | 4 张统计卡:总热点数 / 今日新增 / 紧急热点 / 监控词数 | P0 |
| HP-3 | 多维筛选 | 按来源、重要程度、关键词、时间范围(1h/今天/7d/30d)、真实性筛选 | P0 |
| HP-4 | 多维排序 | 按发现时间、发布时间、重要程度、相关性、综合热度排序 | P0 |
| HP-5 | 热度计算 | 互动量加权(赞×2 + 转发×3 + 评论×5 + 浏览/100…),log10 压缩到 0-100,分"爆/热/温/凉/冷"五级 | P0 |

## 4. 非功能需求

### 4.1 性能

- 页面加载时间 < 3s;API 响应时间 < 1s;
- 支持至少 100 个激活关键词的持续监控;
- 一轮全量巡检(单关键词)建议控制在 2 分钟内。

### 4.2 可用性

- 7×24 运行;单源爬虫失败、AI 服务不可用均不影响主流程;
- 爬虫频率控制(每个源独立限流),避免被封 IP;
- 定时任务异常自动记录日志,不中断后续关键词。

### 4.3 安全

- API Key / SMTP 密码等敏感配置**只存环境变量或本地配置文件**,不写入数据库明文日志;
- 对外接口无鉴权(单用户内网工具),但**禁止**把敏感配置暴露给前端;
- 邮件、搜索接口对输入做长度校验,防注入。

### 4.4 成本控制

- AI 调用可配配额(每轮分析条数上限);
- 查询扩展结果缓存,同关键词不重复调用 AI;
- 邮件仅 high/urgent 发送,可一键关闭。

## 5. 数据源规格

| 来源 | 接入方式 | 需 Key? | 限流 | 关键字段 |
|------|----------|---------|------|----------|
| Twitter/X | twitterapi.io `advanced_search` / `trends` | 是(可选) | 按套餐 | 推文内容、时间、互动、作者信息 |
| Bing | HTML 抓取 `bing.com/search`(`li.b_algo`) | 否 | 5s/次 | 标题、摘要、链接 |
| Google | HTML 抓取 `google.com/search`(`div.g`)(备用) | 否 | 10s/次 | 同上 |
| DuckDuckGo | HTML 抓取 `html.duckduckgo.com/html/`(需解 `uddg=` 重定向) | 否 | 3s/次 | 同上 |
| HackerNews | 官方 API `hn.algolia.com/api/v1/search`(24h 内) | 否 | 1s/次 | 标题、点数、评论数、作者 |
| 搜狗 | HTML 抓取 `sogou.com/web`(替代百度,反爬宽松) | 否 | 3s/次 | 标题、摘要 |
| Bilibili | 公开 API `api.bilibili.com/x/web-interface/search/type`(需 buvid3 cookie 防 412) | 否 | 2s/次 | 播放/点赞/评论/弹幕、UP 主 |
| 微博 | HTML/接口抓取 | 否 | 3s/次 | 内容、互动、作者 |

**统一爬虫策略**:随机 User-Agent 轮换、每源独立 RateLimiter、请求超时 15s、失败静默返回空数组并记日志。

## 6. AI 分析规格

### 6.1 输出协议(JSON,强制)

```json
{
  "isReal": true,
  "relevance": 0-100,
  "relevanceReason": "相关性打分理由(≤200字)",
  "keywordMentioned": true,
  "importance": "low|medium|high|urgent",
  "summary": "此内容与关键词的关联(≤150字)"
}
```

### 6.2 分析要点(prompt 核心规则)

1. 排除标题党、假新闻、营销软文;
2. 相关性必须"直接涉及关键词":仅同领域未提及 ≤ 40 分;直接讨论 ≥ 60 分;间接沾边 30-50 分;
3. 标记是否直接提及关键词或其等价表述;
4. 重要程度 = 对关注该关键词的人而言的重要性;
5. `temperature: 0.2` 保证判断一致性;内容截断 2000 字符。

### 6.3 入库过滤规则(硬编码,在 AI 结果之上)

```
isReal = false            → 丢弃
relevance < 50            → 丢弃
keywordMentioned=false 且 relevance < 65 → 丢弃
```

## 7. 接口设计

### 7.1 RESTful API

```
# 关键词
GET    /api/keywords                # 关键词列表(含热点数统计)
POST   /api/keywords                # 添加 {text, category?}
PUT    /api/keywords/{id}           # 编辑/激活/暂停 {text?, isActive?}
DELETE /api/keywords/{id}           # 删除

# 热点
GET    /api/hotspots                # 分页+筛选+排序
        # query: page, size, source, importance, keywordId, timeRange, isReal, sortBy
GET    /api/hotspots/{id}           # 详情
POST   /api/hotspots/search         # 全网搜索 {query}

# 通知
GET    /api/notifications           # 通知列表(分页)
POST   /api/notifications/read      # 标记已读 {id?}(空=全部)

# 设置
GET    /api/settings                # 全部设置(脱敏)
PUT    /api/settings                # 更新设置

# 运维
GET    /api/health                  # 健康检查
POST   /api/check-hotspots          # 手动触发巡检
```

### 7.2 WebSocket 事件

```
服务端 → 客户端:
  hotspot:new          # 新热点 {hotspot, keyword}
  notification         # 通知 {type, title, content, hotspotId, importance}

客户端 → 服务端:
  subscribe   [kw1, kw2]      # 订阅关键词房间
  unsubscribe [kw1, kw2]      # 取消订阅
```

## 9. 验收标准

### 9.1 功能验收

- [ ] 能添加/编辑/删除/启停关键词,删除后热点仍在
- [ ] 30 分钟定时巡检 + 手动触发均正常,新热点入库并生成通知
- [ ] 多源抓取:单源故障不影响整体结果
- [ ] AI 能正确识别虚假内容、给出 0-100 相关性分与四档重要度
- [ ] 热点列表支持 5 维筛选 + 4 种排序 + 分页,热度等级正确
- [ ] 全网搜索返回聚合结果
- [ ] 浏览器能收到 WebSocket 实时推送,邮件能收到 high/urgent 通知
- [ ] 设置页可改 AI/邮件/巡检配置,保存后立即生效(或重启生效并提示)

### 9.2 性能验收

- [ ] 页面加载 < 3s,列表接口 < 1s(5000 条热点数据下)
- [ ] 100 个关键词巡检一轮不超时、不崩

### 9.3 稳定性验收

- [ ] 拔掉网络/AI Key 置空,系统仍可运行,恢复后自动继续
- [ ] 重复巡检不产生重复热点(幂等)
